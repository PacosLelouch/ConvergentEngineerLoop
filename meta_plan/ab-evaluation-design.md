# CEL 系统有效性 A/B 评价设计

> 对照实验：比较 Agent 在 **使用 CEL 技能** vs **不使用 CEL 技能** 条件下，执行同一批工程任务的表现差异。
> 回答的核心问题：CEL 系统是否让 Agent 的工程任务完成得**更好、更稳、更可控**？

---

## 一、实验设计

### 1.1 实验范式

```
                     ┌─ 对照组 (Control) ──→ 无 CEL，裸 Agent 执行 ──→ 采集结果
                    │
一批工程任务测例 ────┤
                    │
                     └─ 实验组 (CEL)    ──→ 加载 CEL 技能执行      ──→ 采集结果
```

**关键控制变量**：
- 同一次对比中，两个组使用**完全相同的 Agent 模型**（如均为 Claude 4.5 或均为 GPT-4o）
- 同一任务的**初始工程状态完全相同**（git snapshot 还原）
- 两个组**互不感知**，各自独立执行

### 1.2 数据采集点

每次实验采集：

| 采集项 | 说明 | 来源 |
|--------|------|------|
| 任务完成状态 | 成功 / 部分完成 / 失败 | 人工 + 自动化判断 |
| 消耗轮次 | 工作区内容实际变化的 mutation checkpoint 数；只读工具和纯消息不计 | PostToolUse + 文件 manifest |
| Token 消耗 | 总输入/输出 token | Agent API 统计 |
| 耗时 | 墙钟时间 | 计时器 |
| 代码变更统计 | 修改文件数、行数、文件类型分布 | git diff --stat |
| 测试结果 | 初始/最终测试通过数、失败数 | pytest/jest 等 |
| 构建/Lint 结果 | 构建是否通过、类型错误数、Lint 错误数 | 构建日志 |
| 新增错误数 | 修改引入的新测试失败、新 lint 错误 | 对比初始与最终快照 |
| 震荡次数 | 同一文件被来回修改的次数、同一文件连续编辑 5+ 次 | git log 分析 |
| 范围漂移程度 | 修改是否涉及任务描述之外的无关文件/模块 | 人工审查 diff |
| 可回滚性 | 修改后能否通过 `git revert` 干净回滚 | git 操作验证 |
| Agent 输出结构化程度 | 是否含明确的状态识别、误差度量、决策记录 | 人工标注 |

## 二、评价指标体系

五个维度，共计 **22 个指标**。指标分为两类：

- **终点指标（Terminal）**：任务完成后的最终状态，衡量"做得对不对"
- **过程指标（Process）**：执行过程中的行为特征，衡量"怎么做对的"——这是 CEL 价值的核心体现

| 类型 | 维度数 | 指标数 | 说明 |
|------|:------:|:------:|------|
| 终点指标 | 3 | 7 | 传统 A/B 测试通用指标 |
| 过程指标 | 4 | 15 | CEL 差异化价值所在——收敛行为、探索效率、震荡稳定性、决策可追溯性 |

> **关键设计原则**：终点指标容易天花板打平（强模型在可解任务上都能 100% 完成），过程指标才能区分"稳健收敛"和"碰巧成功"。CEL 的理论基础就是通过控制论纪律优化过程，因此过程指标必须丰富。

### 2.1 终点维度一：效果 (Effectiveness) —— 是否完成任务

| 编号 | 指标名 | 类型 | 定义 | 好方向 |
|------|--------|:--:|------|:--:|
| EFF-1 | 任务完成率 | 终点 | 成功完成任务数 / 总任务数 | ↑ |
| EFF-2 | 需求满足度 | 终点 | 人工评分 1-5：最终产物是否满足任务描述的全部要求 | ↑ |
| EFF-3 | 最终测试通过率 | 终点 | 任务完成后全量测试通过数 / 全量测试总数 | ↑ |

### 2.2 终点维度二：质量 (Quality) —— 产出物质量

| 编号 | 指标名 | 类型 | 定义 | 好方向 |
|------|--------|:--:|------|:--:|
| QLT-1 | Lint/类型清洁度 | 终点 | 任务完成后 lint 错误数 + 类型错误数 | ↓ |
| QLT-2 | 最小修改度 | 终点 | 任务实际修改行数 / 必要最少修改行数 | ↓（→1） |
| QLT-3 | diff 精确率 | 终点 | 与任务直接相关的修改行数 / 总修改行数 | ↑（→1） |
| QLT-4 | 回归引入率 | 终点 | 修改后新增测试失败数 / 初始失败数 | ↓ |

### 2.3 过程维度一：收敛效率 (Convergence Efficiency) —— 多快收敛

| 编号 | 指标名 | 类型 | 定义 | 好方向 |
|------|--------|:--:|------|:--:|
| CNV-1 | 收敛轮次 | 过程 | 从 baseline 到首次达到最终误差值的 mutation checkpoint 数 | ↓ |
| CNV-2 | 收敛稳定性 | 过程 | 首次达到最终误差后是否反弹（波动=1-保持最终误差的 checkpoint/达标后 checkpoint） | ↓ |
| CNV-3 | 轮次有效率 | 过程 | 误差下降的 mutation transition / 全部 mutation transition；误差=pytest failed+errors+目标 lint+任务 acceptance failures | ↑ |
| CNV-4 | 平均 Token 消耗 | 过程 | 每任务消耗的总 token（含输入输出） | ↓ |

> **分析策略**：绘制两组每任务“误差-mutation checkpoint”曲线。平台的 assistant message、CodeBuddy `num_turns` 和 Codex 顶层 `turn` 另行保留为成本元数据，不充当工程迭代边界。

### 2.4 过程维度二：探索纪律 (Exploration Discipline) —— 多精确地探索

| 编号 | 指标名 | 类型 | 定义 | 好方向 |
|------|--------|:--:|------|:--:|
| EXP-1 | 范围漂移率 | 过程 | 修改涉及的任务描述外文件数 / 总修改文件数 | ↓ |
| EXP-2 | 无效编辑率 | 过程 | 最终被回滚/覆盖的编辑次数 / 总编辑次数 | ↓ |
| EXP-3 | 文件重复触碰率 | 过程 | 被修改 ≥2 次的文件数 / 被修改的总文件数 | ↓ |
| EXP-4 | 单向编辑比 | 过程 | 编辑操作只增不改的次数 / 总编辑次数（高=改完就过，低=反复修同一处） | ↑ |

> **分析策略**：scope drift 是 CEL "最小更新"协议的直接检验——CEL 应显著降低范围漂移率。无效编辑率和文件重复触碰率检验 CEL 的误差驱动决策是否真的减少了"试错式"探索。

### 2.5 过程维度三：震荡稳定性 (Oscillation Stability) —— 是否反复横跳

| 编号 | 指标名 | 类型 | 定义 | 好方向 |
|------|--------|:--:|------|:--:|
| OSC-1 | 震荡任务率 | 过程 | 出现震荡（同位置连续编辑 ≥3 次 或 方案 A→B→A）的任务数 / 总任务数 | ↓ |
| OSC-2 | 震荡严重度 | 过程 | 震荡任务中，震荡位置的平均被改次数 | ↓ |
| OSC-3 | 回滚正确率 | 过程 | 触发回滚后误差确实下降的次数 / 总回滚次数（只在 CEL 组有意义，Control 组通常不回滚） | ↑ |
| OSC-4 | 首次定位偏差 | 过程 | 第一次修改的位置与最终正确修改位置的距离（文件级：同文件=0, 同级目录=1, 跨目录=2） | ↓ |

> **分析策略**：震荡是经验上弱模型最常陷入的失败模式——修 A 坏 B，改 B 又坏 A。CEL 的误差下降接受/上升回滚协议直接针对震荡设计，这个维度应该是 CEL 最显著的胜出点。

### 2.6 过程维度四：决策可追溯性 (Decision Traceability) —— 有没有讲清楚为什么

| 编号 | 指标名 | 类型 | 定义 | 好方向 |
|------|--------|:--:|------|:--:|
| QLT-5 | Agent 决策可追溯性 | 过程 | 人工评分 1-5：输出中可清晰追溯每轮"为什么改、为什么接受/回滚" | ↑ |
| DEC-1 | 显式假设数 | 过程 | Agent 输出中明确陈述的假设/推论数量 | —（中性） |
| DEC-2 | 验证步骤数 | 过程 | Agent 执行的外部验证次数（运行测试、检查 lint 等） | ↑（但非越多越好） |

> **分析策略**：决策可追溯性是 CEL 协议要求的直接体现——CEL 强制 agent 记录当前状态、误差度量、决策理由。这个维度的差异应该是结构性的（CEL 远高于 Control），而不是偶然性的。

### 2.7 综合评分

$$
S_{\text{overall}} = \underbrace{w_{\text{eff}} \cdot S_{\text{eff}}}_{\text{终点: 0.20}} + \underbrace{w_{\text{qlt}} \cdot S_{\text{qlt}}}_{\text{终点: 0.15}} + \underbrace{w_{\text{cnv}} \cdot S_{\text{cnv}}}_{\text{过程: 0.25}} + \underbrace{w_{\text{exp}} \cdot S_{\text{exp}}}_{\text{过程: 0.10}} + \underbrace{w_{\text{osc}} \cdot S_{\text{osc}}}_{\text{过程: 0.25}} + \underbrace{w_{\text{dec}} \cdot S_{\text{dec}}}_{\text{过程: 0.05}}
$$

**权重设计逻辑**：
- 终点指标权重降低（0.35 total），因为强模型容易天花板打平
- 收敛效率 + 震荡稳定性权重最高（0.50 total），这是 CEL 理论价值所在
- 决策可追溯性权重低（0.05），因为这是 CEL 的结构性优势，几乎必定显著，不需要靠它拉综合分

### 2.5 综合评分

$$
S_{\text{overall}} = w_{\text{eff}} \cdot S_{\text{eff}} + w_{\text{efc}} \cdot S_{\text{efc}} + w_{\text{stb}} \cdot S_{\text{stb}} + w_{\text{qlt}} \cdot S_{\text{qlt}}
$$

建议默认权重：$w_{\text{eff}}=0.30$, $w_{\text{efc}}=0.20$, $w_{\text{stb}}=0.25$, $w_{\text{qlt}}=0.25$

其中每个维度得分 $S_{\text{dim}}$ 为该维度下各指标的归一化加权和（归一化到 [0,1]，好方向为 1）。

## 三、对比分析方法

### 3.1 单任务对比

对每个任务，计算两组的得分差异 $\Delta_{\text{task}} = S_{\text{CEL}} - S_{\text{Control}}$。

### 3.2 跨任务聚合

| 分析角度 | 方法 |
|----------|------|
| 总体效果 | 所有任务的 $\Delta$ 均值 + 置信区间（bootstrap） |
| 按领域分 | 每个参考域下的 $\Delta$ 均值，找出 CEL 在哪些领域收益最大/最小 |
| 按任务复杂度分 | 简单/中等/复杂任务下的 $\Delta$ 均值，验证 CEL 在复杂任务中是否收益更大 |
| 按轮次趋势 | 两组的误差 $E$ 随轮次变化曲线，比较收敛速度和稳定性 |
| 统计显著性 | 配对 t 检验 或 Wilcoxon 符号秩检验 |

### 3.3 定性分析

对每个任务抽取代表性片段：
- 对照组陷入震荡的典型轮次
- 实验组成功回滚退化的典型轮次
- 两组 diff 的 visual diff 对比

## 四、实验条件

### 4.1 需要准备

- **mock 项目仓库**（见 `task-test-cases.md`），每个任务有初始 commit（含故意缺陷）和预期完成 commit
- **Agent 平台**：至少一个（CodeBuddy 或 Claude Code），同一模型
- **评分脚本**：见 `test-harness.md`

### 4.2 不变量保证

| 变量 | 控制方式 |
|------|----------|
| Agent 模型 | 同一模型版本 |
| 初始工程状态 | git reset --hard 到任务初始 commit |
| 任务描述 | 完全相同（对照组不加 CEL 触发词，实验组加） |
| 系统提示词 | 对照组不加 CEL skill；实验组确保 CEL skill 已加载 |
| 外部环境 | 同一机器、同一时间窗口、相同网络条件 |

### 4.3 各平台差异化处理

| 平台 | 对照组 | 实验组 |
|------|--------|--------|
| CodeBuddy | 对话中不加 CEL 触发词，确保 CEL skill 未被自动加载 | 对话中以触发词开头，确保 CEL skill 加载 |
| Claude Code | 对话中不加 CEL 触发词 | 对话中以触发词开头 |
| Codex | 对话中不加 CEL 相关指令 | 对话中以触发词开头 |
