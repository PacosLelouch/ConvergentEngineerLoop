# CEL 任务套件难度与正交性审计

审计日期：2026-07-24

## 结论

原 20 项不适合整体直接用于 CEL 有效性检验：其中只有 9 项在修复 task overlay 后会让 pytest 失败；7 项初始全绿且没有可执行 oracle；T15 的测试甚至与任务目标相反。若全部混跑，过程指标会把“不需要迭代”误当作“快速收敛”，并把文档/设计任务与代码修复任务的不可比结果混在一起。

默认 `primary` 套件改为 12 项：保留 10 项、优化任务描述与外部验收，并新增 T21/T22。旧任务及夹具均保留，默认 runner 不引用。12 项全部具有非零初始误差，且主要失败机制分别覆盖副作用、最小修复、测试诊断、CI、跨工件契约、规模算法、线程同步、级联故障、兼容迁移、证据冲突、幂等原子性、异步清理。

## 审计方法

每项按四个条件评估：

1. **可观测**：初始态必须有稳定、自动化的非零误差；不能依赖 agent 自报。
2. **有迭代空间**：至少存在一次需要诊断或权衡的决策，不能全是机械替换。
3. **有回归机会**：错误修复可能破坏另一条明确契约，才能检验 CEL 的验证/回滚价值。
4. **相对正交**：任务的主要失败机制、工件类型或证据来源至少有一项独特；同类简单任务只保留一个校准项。

pytest 数据来自 base + task/init 的递归 overlay。扩展后的正确 base 为 **123 passed**。`acceptance` 是工作区外验收器，不对 agent 暴露实现答案。

## 默认主套件的正交性

| 任务 | 主要能力轴 | 主要工件 | 关键错误模式 | 自动 oracle |
|---|---|---|---|---|
| T02 | 副作用边界 | Python | 通知失败错误传播到已成功主操作 | pytest |
| T04 | 最小修复校准 | Python | 空集合返回契约 | pytest |
| T05 | 测试诊断 | Python + tests | 产品 bug / 错误断言 / 非确定测试混淆 | pytest + acceptance |
| T10 | 可复现 harness | YAML + requirements | 浮动运行时/依赖和缺失环境 | acceptance |
| T14 | 多工件一致性 | Python + tests + README | 实现修好但边界、编码或文档遗漏 | pytest + acceptance |
| T16 | 算法规模化 | Python | 递归深度随输入规模失效 | pytest |
| T17 | 线程同步 | Python | 实例共享状态竞态 | pytest + AST acceptance |
| T18 | 级联定位 | 3 个 Python 模块 | 上游修复暴露下游失败 | pytest |
| T19 | 兼容性重构 | Python + migration doc | 新流式接口破坏旧路径接口 | pytest + acceptance |
| T20 | 证据驱动修复 | Python + logs + API doc | 声明契约与生产样本冲突 | pytest + acceptance |
| T21 | 可靠性语义 | Python | 重试重复记账、冲突 id、部分提交 | pytest |
| T22 | 异步生命周期 | async Python | 异常/超时/取消留下任务或连接 | pytest |

这不是数学意义上的完全独立：T14/T19/T20 都含文档，T18/T21 都有多条不变量。但它们的**主因**分别是跨工件同步、兼容迁移、证据冲突、分层级联和事务语义。相比原 T01/T03/T04 三个简单代码题以及 T06/T09 的“只补工件”，共线性已显著降低。

复杂度分布为 1 个 simple、3 个 medium、8 个 complex。主实验应按任务配对比较 Control/CEL，并按复杂度分层报告；不能只看 12 项总平均。T04 用于观察 CEL 在简单任务上的协议开销，其余复杂任务用于检验 CEL 的潜在收益。

## 新增任务的意义

### T21：重试幂等性与批次原子性

原套件没有状态机/事务语义。T21 同时要求：相同事件重试不重复记账、冲突事件 id 报错、失败批次无部分提交、失败后可合法重试。局部修补某一测试很容易破坏另一不变量，适合观察小步验证是否有收益。初始信号为 **6 fail / 117 pass**。

### T22：异步取消与资源清理

原并发任务只有线程计数器，没有 async cancellation。T22 区分成功、worker 异常、超时、调用方取消和空输入五条生命周期路径，并检查子任务终止及连接恰好关闭一次。初始信号为 **3 fail / 120 pass**，且会出现未回收 future 警告，能暴露只修 happy path 的方案。

## 实验使用规则

- 默认任务来源只有 `cel-eval-mock-project/task_suite.json` 的 `primary`；`run_config.yaml` 中的旧目录索引不参与遍历。
- T11/T12/T13 单独做盲评定性研究，不进入 CNV/OSC/EXP 的同一统计池。
- 每次运行使用 fresh workspace；task/init 是递归 overlay，不能替换整个 `src` 或 `tests`。
- checkpoint 是实际内容变化，不是 assistant message 或顶层 turn。
- `allowed_paths` 必须任务级显式定义，范围漂移不能从自然语言临时猜测。
- pytest、目标文件 ruff、acceptance 均由外部观察器执行；agent_log 仅可作定性材料，不能作为数值来源。
- 新增/修改任务后先冻结版本并重跑初始信号审计，再开始 A/B；不要根据 A/B 结果回头调整任务。
